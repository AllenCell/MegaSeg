## Key Findings

**1. Classic workflows are fully deterministic across library versions.** We
re-ran all 13 classic `aicssegmentation` workflows on 24 test images and
compared fresh outputs against the existing stored outputs in `ms_classic/`.
Result: **22 of 24 produced bit-identical output (Dice = 1.000)**; only ST6GAL1
showed a minor floating-point difference (Dice = 0.997). Despite major library
upgrades (scikit-image 0.20 to 0.26, numpy 1.24 to 2.4, scipy 1.10 to 1.17),
the workflow outputs have not changed.

**2. The GT masks were not generated by the classic workflow scripts.** We
traced the GT generation back to the original data scripts and found that both
data sources — `test_new.csv` GT files and per-structure `_seg.tiff` files —
were created by separate pipelines that pull from AICS's production
segmentations (`struct_seg_path` in `allcells_beta.csv`), not by executing the
classic workflow notebooks. The observed discrepancies between workflow output
and GT are therefore **structural** (different pipelines with different
parameters), not caused by software version drift.

**3. Reliability varies by structure.** Seven structures have near-perfect
agreement between workflow output and GT (Dice > 0.99), two have moderate
systematic offsets (~0.95), and four have large or variable discrepancies
(Dice 0.60-0.94). This has direct implications for which benchmark comparisons
against this GT can be trusted.

## GT Provenance

### Per-structure CSVs (`14structs_rand/`)

The `_seg.tiff` masks in `14structs_rand/{train,val,test}/` were generated by
`generate_14structs_rand_{train,test,val}.py`. These scripts read
`struct_seg_path` directly from the Allen Cell Collection's `allcells_beta.csv`
manifest and copied the production segmentation to disk — **no workflow was
executed**. The production pipeline may use different algorithms or parameters
than the classic workflow notebooks.

> Source: `/allen/aics/assay-dev/users/Suraj/megaSeg/add_structs/generate_14structs_rand_train.py`

### test_new.csv GT (`general_im_gt/`)

The `_GT.tiff` masks were generated by `oldWork/get_data.py` and
`get_data_v1.py`:

| Structure(s) | GT Source | Notes |
|-------------|-----------|-------|
| FBL | Custom `dot_slice_by_slice` (log_sigma=1, cutoff=0.01) | Different params from classic workflow; explains consistent ~0.64 Dice |
| SEC61B | `struct_seg_path` from Quilt | AICS production pipeline |
| TOMM20, NPM1, NUP153, LAMP1 | `struct_seg_path` (via `get_data_v1.py`) | AICS production pipeline |

All GT was binarized: `str_seg[str_seg > 0] = 1` (values {0, 1}), whereas
classic workflow outputs use {0, 255}. Our comparison script normalizes both
with `(arr > 0)` before computing Dice.

> Source: `/allen/aics/assay-dev/users/Suraj/megaSeg/oldWork/get_data.py`

## Evidence

### Determinism: Fresh vs. Existing Classic Outputs (Phase 3)

Re-ran all workflows on the 24 `test_new.csv` images (2 per structure, 12
structures with existing outputs). Fresh outputs compared against stored
`ms_classic/{STRUCT}/` files:

| Structure | Image 1 | Image 2 |
|-----------|---------|---------|
| ACTN1 | 1.000 | 1.000 |
| CTNNB1 | 1.000 | 1.000 |
| FBL | 1.000 | 1.000 |
| LAMP1 | 1.000 | 1.000 |
| MYH10 | 1.000 | 1.000 |
| NPM1 | 1.000 | 1.000 |
| NUP153 | 1.000 | 1.000 |
| RAB5A | 1.000 | 1.000 |
| SEC61B | 1.000 | 1.000 |
| SON | 1.000 | 1.000 |
| **ST6GAL1** | **0.997** | **0.997** |
| TUBA1B | 1.000 | 1.000 |

ST6GAL1's minor deviation (0.3%) is likely a floating-point sensitivity in its
multi-step filtering pipeline. All other structures are bit-identical.

### Workflow Output vs. GT: Structure Reliability Tiers

Combining Phase 1 (24 images from `test_new.csv`), Phase 2 (81 images from
per-structure CSVs across train/val/test), and Phase 3b (30 test images from
per-structure CSVs):

#### Tier 1 — Reliable GT (Dice > 0.99)

| Structure | N (Phase 2) | Mean Dice | Range | Data Sources |
|-----------|-------------|-----------|-------|--------------|
| NPM1 | 9 | 0.997 | 0.977 - 1.000 | test_new + per-struct |
| TOMM20 | 3 | 1.000 | 0.9996 - 1.000 | per-struct only |
| CTNNB1 | 9 | 0.999 | 0.999 - 1.000 | test_new + per-struct |
| RAB5A | 9 | 0.998 | 0.997 - 0.998 | test_new + per-struct |
| LAMP1 | 2 | 0.999 | 0.998 - 0.999 | test_new only |
| NUP153 | 9 | 0.995 | 0.987 - 0.998 | test_new + per-struct |
| SON | 9 | 0.995 | 0.995 - 0.996 | test_new + per-struct |

These 7 structures' GT masks closely match the classic workflow output.
Benchmark evaluations against this GT are trustworthy.

#### Tier 2 — Usable GT with Caveat (Dice ~0.93-0.97)

| Structure | N (Phase 2) | Mean Dice | Range | Data Sources |
|-----------|-------------|-----------|-------|--------------|
| MYH10 | 9 | 0.961 | 0.949 - 0.976 | test_new + per-struct |
| TUBA1B | 2 | 0.963 | 0.927 - 1.000 | test_new only |

GT is close but not identical. Benchmark results for these structures carry
an inherent ~3-7% Dice uncertainty from the GT generation process itself.

#### Tier 3 — Unreliable GT (Dice < 0.93, high variance)

| Structure | N (Phase 2) | Mean Dice | Range | Key Issue |
|-----------|-------------|-----------|-------|-----------|
| SEC61B | 9 | 0.925 | 0.758 - 0.997 | High per-image variance |
| ST6GAL1 | 9 | 0.905 | 0.867 - 0.999 | High per-image variance |
| ACTN1 | 9 | 0.889 | 0.666 - 0.999 | Bimodal: ~1/3 of images at ~0.67, rest at ~0.999 |
| FBL | 2 | 0.641 | 0.609 - 0.674 | GT used different algorithm (`dot_slice_by_slice` with different params) |

Evaluation against this GT should be interpreted with caution. For ACTN1,
the bimodal pattern suggests the production pipeline handled a subset of
images differently. For FBL, the GT was explicitly generated with a different
segmentation function.

### Structures Without Per-Structure CSVs

Five structures could only be tested against `test_new.csv` (2 images each)
and lack the larger per-structure CSV datasets: CETN2, FBL, LAMP1, SLC25A17,
TUBA1B. Their classification is based on limited data.

## Methodology

### Verification Script

`benchmark/scripts/verify_classic_gt.py` runs all four phases. It dynamically
imports each structure's workflow function from the classic scripts in
`ms_classic/`, applies source patches where needed, runs segmentation, and
computes Dice coefficients.

### Source Patches for Broken Workflows

Four of 17 workflow scripts had breaking incompatibilities. The verification
script applies source-level patches at import time — no original files are
modified:

| Script | Root Cause | Fix |
|--------|-----------|-----|
| LMNB1 | `from skimage.morphology import watershed` removed in skimage 0.26 | Redirect import to `skimage.segmentation.watershed` |
| CETN2 | `peak_local_max` returns Nx3 coordinates instead of boolean mask (skimage 0.26) | Wrapper function converts coordinates back to boolean mask |
| SLC25A17 | Same `peak_local_max` API change as CETN2 | Same wrapper |
| TOMM20 | Module-level notebook code calls `tifffile.read_array()` which uses `ndarray.newbyteorder()` (removed in numpy 2.0) | AST-based source stripping: parse the script, find the last function/import definition, truncate module-level executable code |

### Data Summary

| Phase | What Was Compared | N Images | Purpose |
|-------|-------------------|----------|---------|
| 1 | Existing classic outputs vs. test_new.csv GT | 24 | Baseline discrepancy measurement |
| 2 | Fresh workflow runs vs. per-structure GT | 81 | Larger sample across train/val/test splits |
| 3 | Fresh workflow runs vs. existing classic outputs | 24 | Determinism test (the critical experiment) |
| 3b | Fresh workflow runs vs. per-structure GT (test split only, saved to disk) | 30 | Generate fresh outputs for downstream use |

Total: **159 Dice comparisons** across 10-13 structures (depending on phase).

## Questions for Reviewers

We would appreciate feedback on the following:

1. **Do the findings about GT provenance match your understanding?** The GT
   masks appear to come from AICS's production segmentation pipeline
   (`struct_seg_path` in `allcells_beta.csv`) rather than from the classic
   workflow notebooks. Is this consistent with how the original dataset was
   assembled?

2. **Is the tier classification reasonable?** We propose treating 7 structures
   as having reliable GT, 2 as usable-with-caveats, and 4 as unreliable. Does
   this mapping align with your domain knowledge of these structures?

3. **Should we re-generate GT for the Tier 3 structures?** For ACTN1, FBL,
   SEC61B, and ST6GAL1, the GT masks differ materially from what the classic
   workflows produce. Options include:
   - Accept the current GT as-is (it reflects the production pipeline, which
     may be the intended reference)
   - Re-generate GT by running the classic workflows on all images
   - Use both as separate evaluation targets

4. **FBL specifically:** The GT was generated with `dot_slice_by_slice`
   (log_sigma=1, cutoff=0.01), which is a different function with different
   parameters than the classic FBL workflow. Was this intentional? Should FBL
   evaluation use the workflow output or the `get_data.py` version as GT?

5. **Are there other structures or data sources we should verify?** We tested
   10 of 17 structures against per-structure CSVs and 13 against `test_new.csv`.
   Five structures (CETN2, FBL, LAMP1, SLC25A17, TUBA1B) lack per-structure CSV
   data for broader testing.
